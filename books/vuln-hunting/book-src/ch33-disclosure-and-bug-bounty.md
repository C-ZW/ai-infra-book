# 第 33 章：漏洞揭露、嚴重度量化與 Bug Bounty 實戰運作

前面三十二章，我們一路從單點破口練到了跨層利用鏈與 0-day 挖掘工作流。但當你在本地容器裡看著 PoC 跑通、成功打破系統的安全不變量時，真正的最後一哩路才剛要開始：**怎麼把你手上的技術發現，轉化成對方工程團隊聽得懂、願意立刻排進最高優先級修補、而且完全合法合規的正式漏洞通報？**

不管是給開源專案提 GHSA、向商業公司的 Bug Bounty 計畫送件，還是在自家公司內部推動高風險架構修補，決定對方是「60 秒內確認受理並核發獎金／CVE」，還是「已讀不回、甚至反過來寄律師函」的關鍵，從來不是你的漏洞技術有多花俏，而是三件事：**講清楚可驗證的實質業務影響**、**算準結合真實威脅情報的修補急迫度**，以及**死守協調揭露與法律的安全港紅線**。

---

## 從你已知的出發

為什麼有些套件漏洞在掃描報告上頂著嚇人的 `CVSS 9.1`，資深工程師看了一眼卻說「那個函式在我們的線上服務裡根本連不到，排下個月例行更新就好」；反過來，另一個分數只有 `7.5` 的路由繞過，卻讓整個 SRE 與資安團隊在半夜緊急拉起 `24 小時` 止血戰情室？

因為單看一個靜態的 CVSS 基礎分數，根本分不清「理論上很嚴重」跟「現在全網已經有自動化腳本在狂掃、而且我們的對外閘道正好能被打穿」的差別。當你從「看掃描報告修 Bug 的人」變成「主動挖出漏洞並提出通報的研究員或 AppSec 工程師」，如果只丟出一句「我找到一個 SSRF」或貼一段冰冷的掃描器輸出，通常只會被當成低價值的雜訊打發掉。本章就帶你掌握現代資安界通用的定級語言（**CVSS v4.0 + EPSS + CISA KEV**）、三種真實場景的標準回報 SOP，以及讓分流工程師一看就點頭的 **Impact-first** 報告寫法。

## 機制與推導

### 攻擊者目標與實質影響

在漏洞揭露與分流（Triage）的談判桌上，攻擊者、研究員與防守方其實都在爭論同一個核心問題：**這個技術瑕疵在真實系統裡，到底能換到多少實質利益？**

對攻擊者來說，一個單獨的技術原語（像是噴出錯誤堆疊、或是能多跳一次非預期的網址轉導）本身一毛錢都不值；只有當它能跨過信任邊界、打破我們在第 1 章定義的安全不變量——比如跨租戶偷看別家商戶的帳本、把提領金額無中生有、或摸走雲端 IAM 憑證——才算真正得手。

反過來看防守方與廠商的分流團隊，他們每天要看幾十份甚至上百份通報。如果你的報告沒辦法把「底層的解析錯誤或競態條件」清楚翻譯成「哪個核心業務或下游系統會被打穿」，這份報告馬上就會被歸類成「理論風險」（Theoretical Risk）或「一般硬化建議」（Hardening），最後躺在待辦清單底層石沉大海。所以動筆寫報告前，我們得先學會用一套精確的量化座標，把這條因果鏈釘死。

### CVSS v4.0 向量結構與 v3.1 關鍵差異

過去十年大家看慣的 CVSS v3.1 有兩個一直被工程師吐槽的老毛病：一是只要漏洞需要特定設定或搶併發時間差，大家就只好把攻擊複雜度勾成 `AC:H`，把「要撞破加密或 ASLR 防護」跟「要等某個設定開啟」混為一談；二是只要漏洞跨過元件邊界，就只能勾一個模糊的 `S:C`（Scope Changed），完全看不出到底是閘道器自己掛了，還是後面的資料庫被洗劫了。

FIRST 在 2023 年底正式推出的 **CVSS v4.0**（目前業界正處於 v3.1 與 v4.0 並行的過渡期），就是為了徹底修好這兩個盲點。在看細部指標之前，v4.0 先規定每個分數都必須標明它納入的脈絡層級：

- **CVSS-B**（Base）：純基礎分數。只看漏洞本身固有的特性，不隨時間或部署環境改變，通常由廠商或 NVD 公布。
- **CVSS-BT**（Base + Threat）：加上威脅情報。核心指標是 **E**（Exploit Maturity，利用成熟度），用來標示這個洞現在是只有理論討論、已經有公開 PoC，還是已經在真實網路上被駭客拿來攻擊（Attacked）。
- **CVSS-BE**（Base + Environmental）：加上企業自己的部署環境。除了標註資產的機密／完整／可用性重要度（`CR`、`IR`、`AR`），還可以透過 **Modified Base Metrics**（如 `MAV`、`MAC`、`MAT` 等）按實際網路隔離狀況調整分數——比如某個套件漏洞原本是公網可達（`AV:N`），但你們把它鎖在只有內網跳板機能碰到的子網裡（`MAV:A` 或 `MAV:L`），就能在這裡據實反映。
- **CVSS-BTE**（Base + Threat + Environmental）：把基礎特性、外部威脅跟內部環境全部算進來，這才是決定團隊要不要半夜爬起來修漏洞的最終依據。

而在最核心的基礎指標（Base Metrics）裡，CVSS v4.0 做了兩刀非常貼近現代微服務架構的拆分：

第一刀是**把原本的 `AC` 一分為二，拆成 `AC`（Attack Complexity）與 `AT`（Attack Requirements）**。在 v4.0 裡，**`AC`**（`L`/`H`）只問一件事：「攻擊者需不需要自己動手繞過系統內建的安全防禦機制（像是湊出資訊洩漏來繞過 ASLR）？」而新增的 **`AT`**（`N` None / `P` Present）則專門用來標記：「觸發這個漏洞，需不需要依賴某種特定的部署前置條件或窄小的併發時序視窗？」這樣一拆，像單封包競態（TOCTOU）或需要特定代理設定才能觸發的漏洞，就能精準標成 `AC:L / AT:P`，再也不用委屈塞進 `AC:H` 裡了。

第二刀是**廢掉模糊的 `S`（Scope），直接拆成「脆弱系統自身」（Vulnerable System）與「連帶波及的下游系統」（Subsequent System）兩組獨立的 CIA 影響指標**。現在你可以分別填寫 **`VC` / `VI` / `VA`**（漏洞所在的那個元件自己受了多少傷）以及 **`SC` / `SI` / `SA`**（被它連累的下游微服務、資料庫或宿主機受了多少傷）。在微服務或容器逃逸場景裡，這簡直是神來之筆——你可以清楚寫出「API 閘道本身完全沒當機（`VA:N`），但攻擊者已經穿過它把後端 PostgreSQL 帳本看光並改掉了（`SC:H / SI:H`）」。

我們直接拿第 32 章在 **NexusPay** 串出來的跨系統漏洞（攻擊者需持有一般登入商戶帳號 `PR:L`，依賴特定反向代理與內網轉發組態 `AT:P`，得手後能讀寫閘道憑證並直接打穿下游帳本服務的機密性與完整性），把 v3.1、v4.0 與全書基準的 SLA 分流規則擺在一起算一遍：

```text
情境：NexusPay 跨層授權與內部服務邊界繞過（需已登入一般商戶帳號，且依賴特定代理組態條件）

[1] 舊版 CVSS v3.1 算分
    向量字串 : CVSS:3.1/AV:N/AC:H/PR:L/UI:N/S:C/C:H/I:H/A:N
    為什麼卡 : 因為需要特定代理設定與併發時序，只能硬勾 AC:H；
               跨元件打到後面不同權限管轄的帳本資料庫，只能籠統勾個 S:C。
    算出分數 : 8.2 (High)

[2] 新版 CVSS v4.0 算分（CVSS-B 基礎分數）
    向量字串 : CVSS:4.0/AV:N/AC:L/AT:P/PR:L/UI:N/VC:H/VI:H/VA:N/SC:H/SI:H/SA:N
    逐項拆解 :
      - AV:N (公網可達) / PR:L (只需一般商戶帳號) / UI:N (不用騙受害者點連結)
      - AC:L (不需額外繞過密碼學或記憶體保護機制)
      - AT:P (有特定的代理部署與時序前置條件)
      - VC:H, VI:H, VA:N (出事的閘道元件自身憑證與完整性失守，但服務沒掛)
      - SC:H, SI:H, SA:N (下游的帳本微服務機密與完整性雙雙遭到高程度破壞)
    算出分數 : 8.8 (High)

[3] 加上真實威脅情報後的 SLA 分流決策（對齊全書基準門檻）
    全書基準規則：高危 SLA = 7 天；嚴重 SLA = 24 小時；
                  只要 EPSS >= 0.1 或列入 CISA KEV，一律視為立即處置（升級為 24 小時 SLA）。
    - 狀況 A（自家內部剛挖到的私密漏洞，外面還沒人知道）：
      EPSS = N/A (還沒有公開 CVE)，不在 CISA KEV 裡 -> 照 High (8.8) 排入「7 天」SLA。
    - 狀況 B（來自某個已公開 CVE 的開源相依元件，查 FIRST API 拿到 EPSS = 0.24150）：
      因為 EPSS = 0.24150 >= 0.1 -> 直接觸發立即處置門檻，從 7 天強制升級為「24 小時」SLA！
```

### EPSS 與 CISA KEV：從「理論嚴重度」到「真實被利用機率」

為什麼上面狀況 B 看到 `EPSS = 0.24150`，就要立刻把修補時限從 `7 天` 拉警報縮短到 `24 小時`？

因為光看 CVSS 基礎分數，你永遠不知道「現在此時此刻，外面的駭客和殭屍網路到底有沒有在打這個洞」。真實世界裡，有太多 CVSS 9.0 以上的漏洞因為觸發條件太冷門、或者根本沒人寫出好用的利用工具，放了三年都沒半個攻擊封包；反倒是某些 CVSS 只有 7.5 左右的身分繞過或反序列化漏洞，因為一發 `curl` 就能打穿，成了全網勒索軟體最愛的破門槌。

為了不讓工程師天天為了紙老虎加班，現代漏洞管理都把 **CVSS v4.0** 搭配另外兩個真實威脅指標一起看：

第一個是 **EPSS**（Exploit Prediction Scoring System，漏洞利用預測評分系統）。它是由 FIRST 維護的資料驅動模型（2025 年 3 月已升級到 v4），每天收集全網的威脅情資、公開 PoC 與掃描紀錄，幫每一個已編號的 CVE 算出兩個浮點數（介於 `0.0` 到 `1.0` 之間）：
- **Score**：預測這個 CVE 在**未來 30 天內**，在真實網路上被駭客拿來攻擊的機率。比如前面算的 `0.24150`，就代表未來一個月內有高達 `24.15%` 的機率會挨打。
- **Percentile**：這個分數在所有已知 CVE 裡面排在百分之幾（例如 `0.96` 就代表它比全網 `96%` 的漏洞都還要危險）。
最方便的是，FIRST 提供了完全免申請金鑰的公開 REST API（`https://api.first.org/data/v1/epss?cve=CVE-YYYY-XXXX`），寫十幾行腳本就能直接接進你們的 CI/CD 分流管線。

第二個是 **CISA KEV**（Known Exploited Vulnerabilities Catalog，已知被利用漏洞目錄）。如果說 EPSS 是精準的「氣象預報（降雨機率）」，那美國 CISA 維護的 KEV 清單就是「**外面已經在下暴雨了**」的既成事實（`true` 或 `false`）。只要一個 CVE 被塞進 KEV 清單，就代表真實世界裡已經確認有駭客拿它攻破過系統。

把這三個指標合在一起，我們的分流鐵律就非常清晰了：**CISA KEV 是絕對不能妥協的底線，只要命中 KEV 或是 CVSS 達嚴重等級（`≥ 9.0`），一律直接進 `24 小時` 緊急修復；而對於還沒進 KEV 的漏洞，只要 `EPSS ≥ 0.1`（未來 30 天被攻擊機率超過 10%），就同樣拉起立即處置警報**，讓團隊在攻擊浪潮撲過來之前先把大門鎖死。

### 協調漏洞揭露（CVD）、GHSA 與 CVE 申請流程

當你挖到一個真實的 0-day 漏洞時，接下來要面對的問題是：「我該怎麼通知作者？什麼時候可以把技術文章發出來？怎麼拿到正式的 CVE 編號？」這整套遊戲規則就叫做**協調漏洞揭露**（Coordinated Vulnerability Disclosure, CVD）。

CVD 的精神很單純：既不能讓廠商把漏洞偷偷摸摸壓下來不修，也不能在大家根本還沒有修補版本可以升級的時候，就把攻擊腳本丟到公開網路上害死所有用戶。業界公認的標準協調期限通常是 **90 天**（如果漏洞已經在野外被駭客積極利用，期限常會縮短到 7 天或 14 天；反過來，如果維護者很積極在修、但因為牽涉到多家下游供應鏈需要同步發版，雙方也可以協議稍微展延幾天）。

在開源世界裡，現在最順手的端到端通報管道就是 **GitHub Security Advisories**（GHSA）：

首先，只要開源專案有打開 **Private Vulnerability Reporting**（私密漏洞回報），你點進倉庫的 `Security` 分頁就會看到 `Report a vulnerability` 按鈕。點下去填好送出，GitHub 就會開一個只有你跟專案維護者看得到的私密草稿（Draft Advisory），維護者還可以在裡面直接開一個隔離的暫存私有分支（Temporary Private Fork）跟你一起測試修補程式，完全不怕 Commit 紀錄在發版前走漏風聲。

接著是申請 **CVE 編號**。CVE ID 是由 MITRE 授權的各家 **CNA**（CVE Numbering Authorities，CVE 編號管理機構）負責核發的。像微軟、Google、AWS 這些大廠本身就是 CNA，而 **GitHub 自己也是官方認證的 CNA**。只要你們在 GHSA 裡確認漏洞屬實、修補版本也準備好了，維護者在 GHSA 畫面上按一個鈕就能直接向 GitHub CNA 申請 CVE 編號。等新版一發佈、維護者按下 Publish Advisory，這張 CVE 就會正式生效（從 `RESERVED` 變成 `PUBLISHED`），而且 GitHub 的 Dependabot 還會自動幫全世界的下游用戶跳出升級通知。

至於那些沒放在 GitHub 上、而且廠商自己也不是 CNA 的軟體，則可以透過 MITRE Root CNA 或是各地的協調中心（像是台灣的 **TWCERT/CC** 或美國的 **CERT/CC**）幫忙申請編號與轉達通報。

### 發現真實漏洞後的回報與處置標準作業流程（SOP）

很多技術很強的工程師第一次挖到真實漏洞時，不是栽在技術分析，而是栽在「走錯通報管道」——有人好心直接發了一個公開的 Pull Request 幫開源專案修洞，結果半小時後全網的自動化掃描機器人就照著他的 Commit Diff 開始狂打還沒升級的伺服器；也有人對著沒有授權的商業網站猛測猛撈，結果獎金沒拿到先收到警局通知書。

請把下面這三套不同場景的標準作業流程（SOP）當成你的實戰護身符：

#### 情境一：開源專案（Open-Source Repositories）

1. **先找 `SECURITY.md`**：動手回報前，先看專案根目錄或 `.github/` 目錄下有沒有 `SECURITY.md`，確認作者指定的安全聯絡信箱、PGP 公鑰或私密通報入口。
2. **走私密通道，絕對禁止開公開 Issue 或公開 PR**：如果專案在 GitHub 上且有開私密回報，直接走 `Security -> Advisories -> Report a vulnerability` 建立 **GHSA 草稿**；如果沒開，就寄信到 `SECURITY.md` 上的安全信箱。**千萬、絕對不要直接開公開的 GitHub Issue，也不要直接發帶修補程式碼的公開 Pull Request**——公開 PR 的 diff 跟測試案例，在駭客眼裡就是現成的 0-day 武器說明書。
3. **申請 CVE 並對齊 90 天揭露期**：在 GHSA 的私有分支裡協助維護者確認修補有沒有被繞過，並請維護者（或透過 GitHub CNA）申請 CVE 編號。雙方約定好 90 天協調揭露視窗，等修補版正式釋出、大家有得升級之後，再發表你的技術分析文章。

#### 情境二：外部商業網站與服務（External Commercial Services）

1. **先查 `security.txt` 與授權範圍（Scope）**：在對任何商業服務做深入測試前，先看它的 `https://<domain>/.well-known/security.txt`（遵循 **RFC 9116** 標準），或是到 **HackerOne、Bugcrowd、Intigriti** 等平台上查清楚它有沒有公開的 VDP（漏洞揭露計畫）或 Bug Bounty。一字一句核對哪些網域跟 IP 在授權範圍內（`In-Scope`），哪些動作被明文禁止（多數計畫都嚴禁社交工程、DDoS 與高頻自動化掃描）。
2. **拿到最小證明就立刻停手（Stop at Minimal Proof）**：一旦你的測試已經足以證明邊界失守——比如用自己的帳號 A 讀到了自己註冊的帳號 B 的一筆測試欄位，或是證明 SSRF 能摸到內部中繼資料的端點名稱——**請立刻停手！** 嚴禁下載、傾印或外傳任何真實客戶的資料，嚴禁順著內網繼續橫向移動，也嚴禁改動線上環境的系統設定。
3. **死守 Safe Harbor，遇到無 VDP 廠商走第三方協調**：只在有明確 Safe Harbor（安全港條款）保護的範圍內測試。如果你只是在正常使用某個台灣或國外商業網站時「不小心踩到」明顯的漏洞，但對方**完全沒有公開 VDP 也沒寫 `security.txt`**，千萬別自己寫腳本反覆去戳，更別直接寄信去跟對方談價錢；最安全、法律風險最低的做法，是把你手上已經看到的最小證據交給中立的第三方協調機構（例如台灣的 **TWCERT/CC** 或國際上的 **CERT/CC**），由他們出面聯絡廠商。

#### 情境三：企業內部系統（Internal Company Systems）

1. **走公司指定的加密資安通道並定級分流**：透過公司內部的專責資安事件管道、權限控管工單或 Product Security 信箱回報，並直接套用我們前面學的 **CVSS v4.0 + EPSS/KEV** 算出初步定級，對齊 **`24 小時`（嚴重）** 或 **`7 天`（高危）** 的修復 SLA。
2. **先止血（Containment）再慢慢動手術**：在業務開發團隊還沒把底層程式碼徹底修好之前，先請 SRE 與資安團隊做緊急止血——像是先關掉出事的 Feature Flag、吊銷可能外洩的 Token，或是在 API Gateway / WAF 上先擋掉異常的參數格式。
3. **根因修補、補回歸測試與注意通訊軟體保密**：等開發團隊把架構級修補（像第 34 章的 Paved Road）寫好、而且把防復發的自動化回歸測試加進 CI 之後，才能把臨時止血規則拿掉。特別注意：**在整個救火過程中，絕對不要在 Slack 或 Teams 的大群組裡直接貼出沒打碼的明文 PoC、真實客戶的 JWT Token 或完整攻擊請求**，所有敏感證據只能留在有權限控管的資安工單裡面。

### 高品質漏洞報告結構：Impact-first 與最小可重現原則

站在廠商分流工程師（Triage Engineer）的角度想一想：他早上打開電腦，信箱裡躺著 50 封漏洞報告。是什麼決定了你的報告在 60 秒內被蓋上 `Triaged`（確認受理）進入發獎金流程，而不是被退回 `Needs More Info` 甚至直接關單？

答案就是採用 **Impact-first**（影響優先）的五段式結構：

第一段是**直擊痛點的標題與一行摘要**（Title & Executive Impact）。千萬別寫「`/api/v1/export` 參數沒過濾」這種讓人摸不著頭緒的標題；要寫「**一般登入商戶可透過 `/api/v1/export` 的路徑解析差異，跨租戶讀取任意商戶的結算帳本明細（BOLA + 路由分歧）**」。開頭第一句就直接講明：誰（什麼權限）、打哪個元件、能造成什麼具體的業務或系統破壞。

第二段是**量化評分與環境條件**。附上完整的 CVSS v4.0 向量字串與分數，並用兩三句話講清楚你為什麼這樣勾（特別是 `AT` 需要什麼前置條件，以及 `SC/SI` 波及了哪個下游系統）。

第三段是**精準的根因定位**（Root Cause）。直接點出是哪一道信任邊界上的哪一條安全不變量破了功（例如前端閘道與後端微服務對路徑正規化的順序不一致，或是扣款 SQL 漏了租戶條件），而不是把掃描器的幾百行 log 原封不動貼上去。

第四段是**複製貼上就能跑通的最小可重現步驟**（Minimal Reproducible PoC）。給出一條精簡乾淨的 `curl` 指令或短短十幾行的重現腳本，讓分流工程師不用猜參數就能在 3 分鐘內重現出來。如果要測越權（BOLA），一律**自己註冊兩個測試帳號（Account A 與 Account B）**，拿 A 的 Token 去讀 B 的測試資料，證明完全沒有碰觸任何真實用戶。

第五段是**可落地的架構修補建議**（Remediation）。給出符合該語言與框架習慣的根治做法（比如「在共用資料庫封裝層強制由已驗證的 JWT 綁定 `tenant_id`」），並順手附上修好之後該怎麼寫回歸測試。

### 實際回報時的必備資料清單與注意事項（紅線清單）

每次準備按下送出鍵之前，請拿下面這兩份清單逐項打勾，確保你的報告既能讓分流人員在 3 分鐘內重現受理，又不會踩到任何一條法律與道德紅線：

#### 一、提交報告必備的 5 項資料清單（Submission Package）

1. **精確的目標座標與版本資訊**：寫清楚出事的網域、API 完整路徑與參數名稱；如果是開源專案，要附上確切的版本號、`git commit SHA` 以及你的測試執行環境（作業系統、Runtime 版本與開啟的設定旗標）。
2. **影響優先摘要**（Impact-first Summary）：標出對應的 CWE 分類（例如 `CWE-639` 或 `CWE-862`）、攻擊者需要的最低起始權限與環境條件（`PR` / `AT`），以及一句話講完的實質業務破壞面。
3. **3 分鐘內可重現的最小步驟**：附上乾淨的原始 HTTP 請求與回應片段、一鍵執行的 `curl` 指令或精簡 Python 腳本，並標註你測試當下的 **UTC 時間戳記**與你自己的測試帳號 ID（方便對方去伺服器 log 裡對照）。
4. **打碼脫敏後的佐證截圖或 Log**：附上關鍵的回應標頭、ASan 崩潰輸出或操作錄影；只要畫面裡有不小心掃到的真實姓名、信箱或憑證碎片，一律先打碼遮罩，而且在對方確認受理後立刻把本機的暫存敏感檔案刪乾淨。
5. **客觀的嚴重度向量與根因修補建議**：附上完整的 CVSS v4.0 向量字串、逐項勾選理由，以及針對程式碼根因的具體修法。

#### 二、回報過程絕對不能踩的 4 條法律與操作紅線

1. **雙測試帳號原則與最小驗證即止步**：測越權或租戶隔離時，永遠只拿自己註冊的兩個測試帳號互打；一旦拿到最小證明就立刻收手，**絕對禁止撈取、儲存或外傳真實用戶資料，也禁止修改正式環境的系統狀態**。
2. **零破壞性測試**：嚴禁對線上環境跑任何會造成服務卡頓、崩潰或資料損毀的操作，包括高頻併發壓測、DDoS、執行 `DROP/DELETE` 刪資料，或是留下一隻持久化後門。
3. **嚴禁未修補前搶先公開**：在協調揭露（CVD）期限到期且修補版本正式發佈之前，絕對不能把 PoC 推上公開 GitHub、發到 X/Twitter 或技術論壇，也不能把沒脫敏的客戶請求丟進未經授權的外部線上網站或公有 AI 聊天框裡。
4. **守住專業溝通底線**：絕對不要用「不給獎金／不調高嚴重度，我明天就公開 0-day」這種話去威脅廠商（這在法律上極容易踩進恐嚇取財紅線）。全程保留帶時間戳記的溝通紀錄；如果覺得對方把嚴重度判太低，就拿實質影響鏈與 CVSS v4.0 的規範條文出來理性舉證。

## 故障模式與防禦

搞懂報告怎麼寫之後，為什麼很多工程師去打 Bug Bounty 或在公司內部推資安修補時，還是常常覺得事倍功半？通常不是因為挖漏洞的技術不夠，而是掉進了下面這四個運作與法律上的大坑。

### 故障模式 1：在紅海目標裡硬撞，時間投資報酬率（ROI）趨近於零

如果你打開 HackerOne 或 Bugcrowd，直接挑一個已經上線五年、獎金最高的大廠主網域（像是某知名跨國電商的首頁），然後拿現成的掃描器去跑，那你花 40 個小時好不容易找到的一個中危邏輯洞，送出去 10 分鐘後十之八九會收到一張冷冰冰的 `Duplicate`（重複回報——別人三個月前就報過了）。

公開 Bug Bounty 平台是非常極端的紅海長尾分布。想要拉高你的時間投資報酬率，選標時要專挑「**自動化掃描器看不懂、而且剛長出來的新鮮攻擊面**」：

- **剛上線的新功能、大改版或剛併購進來的子公司服務**：大企業買下新創公司後，常常急著把新系統直接掛到原本的 SSO 與 API 閘道後面。這時候兩套系統對 JWT 欄位、租戶 ID 或權限角色的解讀最容易對不攏，正是第 32 章講的跨層利用鏈溫床。
- **商業邏輯厚重或走自訂二進位協定的系統**：全自動掃描器很會找已知的 CVE 和表層 XSS，但遇到「多步驟結帳加退款的狀態機競態」、「跨幣別匯率換算的整數捨入漏洞」或是「Webhook 簽章驗證搭配反向代理逾時」就完全瞎了。這反而是懂系統設計的後端工程師最能輾壓全場的主場。
- **大廠核心產品底層依賴的開源解析庫**：很多大公司的外部網站被守得固若金湯，但他們的核心業務其實重度依賴某幾個開源的檔案解析器、RPC 框架或影像處理庫。直接把那幾個開源專案拉回本機跑結構化 Fuzzing 或 CodeQL 變體分析，挖到底層 0-day 後不僅能透過 GHSA 拿正式 CVE，如果同時符合大廠的開源獎勵範圍，還能一舉兩得。

### 故障模式 2：一直收到 `Duplicate`、`Informative` 或 `N/A`

收到 `Duplicate` 至少代表你挖洞的方向是對的，只是手腳慢了點；但如果是連續收到 `Informative`（僅供參考，不修也不給獎金）或 `Not Applicable (N/A)`（無效報告，甚至還倒扣你的平台信譽分數），那就得趕快檢討是不是踩了這三個雷：

第一個雷是**沒看清楚 Scope 就亂打**。很多公司主網域底下的 `support.example.com` 其實是外包給第三方 SaaS 客服系統代管的，或者是計畫明文寫在 `Out-of-Scope` 清單裡的排除項目（像是「缺 SPF/DMARC 郵件紀錄」、「沒敏感操作的 Clickjacking」或「純掃描器吐出來的舊版 TLS 警告」）。送這些上去一定秒退。

第二個雷是**只報了一個「半成品原語」，沒證明實質影響**。比如你發現某個內部錯誤頁面會噴出 Stack Trace 或框架版本號，連怎麼拿它去串出越權或內網穿透都沒寫，就直接當成一個漏洞送出去。在分流人員眼裡，這就只是個沒有立即危害的資訊揭露。

第三個雷是**沒先翻過人家的 Release Notes 跟已知 Issues**。打針對開源專案或有公開版本號的商用軟體時，送件前一定要先去翻翻人家最近兩週的 Changelog 跟 GHSA 列表，免得興沖沖報了一個作者上禮拜五才剛發版修掉的舊洞。

### 故障模式 3：不小心跨出 Safe Harbor，踩進刑法紅線

這一點怎麼強調都不為過：**沒有任何一筆漏洞獎金，值得你拿前科去換。**

不管是台灣《刑法》第三十六章的「妨害電腦使用罪」（第 358 條無故入侵電腦罪、第 359 條無故取得刪除變更電磁紀錄罪、第 360 條無故以電腦程式干擾他人電腦系統罪），還是美國的《電腦詐欺與濫用法案》（CFAA），法律條文看的都是「**你有沒有經過授權**」。

企業在 VDP 或 Bug Bounty 頁面上寫的 **Safe Harbor**（安全港條款），是企業給善意研究員的一張免死金牌——承諾「只要你乖乖照著我們定的範圍跟規則測，就算不小心戳破了系統，我們也不會告你」。但請記住，這把保護傘在下面四種情況下會**當場失效**：

1. **打到 Scope 以外的機器**：計畫只授權測 `*.api.example.com`，你順手去打他們家沒列在上面的內部員工系統或子公司網域，法律上就等於無故入侵。
2. **為了證明自己很厲害而過度撈資料**：你明明讀到第 1 筆自己的測試帳號資料就已經證明 SQL 注入或 BOLA 存在了，卻還寫腳本把人家資料庫裡 10 萬筆真實客戶的姓名電話全倒出來存進自己電腦。就算你發誓沒拿去賣，光是「無故取得大量電磁紀錄」這件事本身就已經跨過犯罪紅線，Safe Harbor 絕對保不了你。
3. **跑去跟沒辦 Bug Bounty 的公司「談條件」**：自己跑去掃一家沒有公開獎金計畫的公司，然後寄信說「我找到了你們的大漏洞，先匯一萬美金顧問費過來我才告訴你們在哪裡」。這在法院眼裡不叫資安研究，叫恐嚇取財。
4. **開高併發腳本把人家線上服務打掛**：為了測競態或 Fuzzing，直接對著線上生產環境每秒狂發幾千個請求，害正常客戶無法結帳，直接觸犯干擾電腦系統罪。

### 故障模式 4：在公司內部推修補時，拿假警報轟炸開發團隊

如果你是公司內部的 AppSec 工程師，最忌諱兩件事：一是把商業掃描器吐出來的幾百頁 PDF 原封不動丟給後端團隊叫他們照單全修；二是死抱著 CVSS Base Score 不放，硬逼大家放下手邊的產品上線去修一個根本在內網離線批次裡、外部完全連不到的 `CVSS 8.8` 相依套件漏洞。

這樣搞個兩次，開發團隊就會把資安部門當成專門找麻煩的穀倉。真正能贏得工程團隊尊重的做法，就是我們在這一章推導的：**先幫開發者做好可達性確認、套上 CVSS-BTE（結合環境與 EPSS/KEV 威脅情報）篩出真正火燒眉毛的 `24 小時` 與 `7 天` 項目，並且附上 3 分鐘就能在本地重現的最小 PoC 與架構修法。**

## 動手做

- **難度**：進階
- **預估時間**：60 分鐘

這個練習我們分成兩個實戰任務：一是幫第 32 章抓到的 NexusPay 跨系統攻擊鏈寫出一份可以直接送審的 **Impact-first 標準漏洞報告**，並寫一支 Python 腳本自動串接 FIRST 的公開 EPSS API 做 SLA 分流；二是寫一支完全合規的被動檢查腳本，幫你自動盤點目標的 `security.txt` 與 `SECURITY.md` 揭露管道，並訂出你自己的 12 週實戰挖掘計畫。

### 任務 1：撰寫 NexusPay 跨系統漏洞報告與 EPSS 自動分流腳本

1. 在本地建一個檔案 `reports/nexuspay-ch33-advisory.md`，把前面「機制與推導」算過的 NexusPay 跨層授權與內網邊界繞過案例，寫成一份完整的 **Impact-first 漏洞報告**。
2. 報告裡必須包含這五塊核心內容：
   - **標題與第一段執行摘要**（一眼看懂受影響元件、所需權限與帳本不變量怎麼被打破）。
   - **CVSS v4.0 完整向量與拆解說明**（清楚寫出為什麼勾 `AC:L` 與 `AT:P`，以及 `VC/VI/VA` 跟 `SC/SI/SA` 是怎麼分開算的）。
   - **威脅情報與 SLA 分流決策**（寫一支 Python 腳本去打 FIRST 的公開 EPSS API 查真實 CVE 的 `epss` 與 `percentile`，並結合 `EPSS ≥ 0.1` 與 CISA KEV 規則，自動印出該排進 `24 小時` 還是 `7 天` SLA）。
   - **最小可重現的防禦性驗證步驟**（只用本地自己建的雙測試帳號驗證邊界，不放任何具破壞性的攻擊 Payload）。
   - **根因定位與架構級修補建議**。
3. 寫完後，拿下面四個問題自己檢查一遍（四題都要能打勾才算過關）：
   - [ ] 第一段有沒有在三句話內講清楚實質業務損失？
   - [ ] CVSS v4.0 向量有沒有把 `AT` 跟下游系統影響（`SC/SI/SA`）拆開寫對？
   - [ ] 重現步驟是不是只動到測試者自己建的隔離帳號，百分之百不碰真實用戶資料？
   - [ ] 修補建議有沒有針對根因，並講清楚修好後怎麼做回歸測試？

### 任務 2：寫一支合規揭露管道盤點腳本與 12 週實戰計畫

1. 去 HackerOne / Bugcrowd 的公開目錄或 GitHub 上，挑 2 個明確設有公開 VDP 或 Bug Bounty 政策的企業或大型開源專案。
2. 寫一支 Python 腳本 `tools/check_disclosure_surface.py`，對目標做**純被動、只發單次 GET** 的合規通報管道檢查：
   - 檢查目標網域底下的 `/.well-known/security.txt` 在不在，有的話就把裡面的 `Contact:`、`Policy:`、`Expires:` 與 `Canonical:` 欄位印出來。
   - 如果是 GitHub 開源專案，就檢查倉庫根目錄或 `.github/` 底下有沒有放 `SECURITY.md`。
3. 寫一份 `12-week-hunting-plan.md`，規劃你接下來 12 週的實戰節奏（例如：第 1–4 週專攻協定解析與多租戶授權邊界、第 5–8 週幫選定的開源目標寫 CodeQL 查詢與 Fuzzing Harness、第 9–12 週深挖複雜商業邏輯並複盤通報品質），同時定下每週可量化的追蹤指標（看了幾行核心程式碼、寫了幾條 CodeQL 規則、送出報告的有效受理率與重複率）。

#### 任務 1 參考實作：EPSS / KEV 自動化分流腳本與報告查核重點

下面這支 Python 腳本直接呼叫 FIRST 官方免金鑰的公開 EPSS REST API（純唯讀查詢公開統計資料），並結合 CISA KEV 與 CVSS v4.0 分數自動判定修復 SLA：

```python
import json
import urllib.request

def fetch_epss(cve_id: str) -> tuple[float, float]:
    url = f"https://api.first.org/data/v1/epss?cve={cve_id}"
    req = urllib.request.Request(url, headers={"User-Agent": "vuln-hunting-triage/1.0"})
    with urllib.request.urlopen(req, timeout=10) as resp:
        payload = json.loads(resp.read().decode("utf-8"))
    data = payload.get("data", [])
    if not data:
        return 0.0, 0.0
    return float(data[0]["epss"]), float(data[0]["percentile"])

def decide_sla(cvss_v4_score: float, epss_score: float, in_cisa_kev: bool) -> str:
    if in_cisa_kev or epss_score >= 0.1 or cvss_v4_score >= 9.0:
        return "24 小時（嚴重／立即處置）"
    if cvss_v4_score >= 7.0:
        return "7 天（高危修復）"
    return "30 天（常規排程）"

if __name__ == "__main__":
    # 拿歷史知名的公開 CVE 測試 API 回傳格式與分流邏輯
    cve = "CVE-2021-44228"
    epss, pct = fetch_epss(cve)
    sla = decide_sla(cvss_v4_score=8.8, epss_score=epss, in_cisa_kev=True)
    print(f"CVE={cve} | EPSS={epss:.5f} (percentile={pct:.5f}) | SLA={sla}")
```

跑完這支腳本，你會看到 `api.first.org` 即時回傳該 CVE 的 `epss` 與 `percentile` 浮點數；只要 `in_cisa_kev=True` 或是 `epss >= 0.1`，就算原本的 CVSS v4.0 基礎分數是 `8.8`（High），`decide_sla()` 也會自動把它拉升到 `24 小時（嚴重／立即處置）`。在你的報告檔案裡，請確認向量字串 `CVSS:4.0/AV:N/AC:L/AT:P/PR:L/UI:N/VC:H/VI:H/VA:N/SC:H/SI:H/SA:N` 與內文推導完全一致。

#### 任務 2 參考實作：合規揭露管道檢查腳本

```python
import urllib.request
import urllib.error

def inspect_security_txt(domain: str) -> None:
    url = f"https://{domain}/.well-known/security.txt"
    req = urllib.request.Request(url, headers={"User-Agent": "security-txt-checker/1.0"})
    try:
        with urllib.request.urlopen(req, timeout=10) as resp:
            body = resp.read().decode("utf-8", errors="replace")
            print(f"[FOUND] {url} (HTTP {resp.status})")
            for line in body.splitlines():
                if line.startswith(("Contact:", "Policy:", "Expires:", "Canonical:", "Acknowledgments:")):
                    print(f"  {line}")
    except urllib.error.HTTPError as e:
        print(f"[MISSING] {url} returned HTTP {e.code}")
    except Exception as e:
        print(f"[ERROR] {url}: {e}")

def inspect_github_security_md(repo: str) -> None:
    url = f"https://raw.githubusercontent.com/{repo}/main/SECURITY.md"
    req = urllib.request.Request(url, headers={"User-Agent": "security-md-checker/1.0"})
    try:
        with urllib.request.urlopen(req, timeout=10) as resp:
            print(f"[FOUND] {url} (HTTP {resp.status})")
    except urllib.error.HTTPError as e:
        print(f"[MISSING] {url} returned HTTP {e.code}")
    except Exception as e:
        print(f"[ERROR] {url}: {e}")

if __name__ == "__main__":
    # 只做單次標準公開檔案讀取，完全符合最低互動原則
    inspect_security_txt("example.com")
    inspect_github_security_md("example/repo")
```

### 參考解答

1. **拆解 CVSS v4.0 向量指標**：
   - **正確填法**：`AC:L`（不需要繞過額外防禦控制）、`AT:P`（需要目標開啟特定非預設設定，且要命中多執行緒競態時間窗）。系統影響則是 `VC:N / VI:N / VA:N`（出事的轉發閘道自己沒崩潰也沒掉資料），以及 `SC:N / SI:H / SA:N`（連累下游的內部結算微服務遭到高程度的完整性破壞）。
   - **為什麼比 v3.1 精準**：以前在 v3.1，只要看到「需要非預設設定＋競態時間窗」，大家就只能把攻擊複雜度勾成 `AC:H`，跟那種「要自己寫 ROP 鏈繞過 ASLR」的硬核防禦混在一起；而且跨到下游服務也只能籠統勾個 `S:C`。v4.0 把外在環境前提拆給 `AT`，又把自身（`V*`）跟下游（`S*`）影響分家，一眼就能看清跨層破壞的真相。
2. **EPSS 與 CISA KEV 的修補優先序對決**：
   - **漏洞乙**必須立刻升級排進 **`24 小時` SLA**；漏洞甲則維持原本 High 等級的 `7 天` SLA（若經可達性分析確認離線環境完全無外部輸入曝險，還可依第 34 章的豁免程序排入常規維護）。
   - **理由**：照全書基準門檻，只要 `EPSS ≥ 0.1` 或列入 CISA KEV，就代表真實世界裡的攻擊浪潮已經近在眼前（漏洞乙未來 30 天內挨打的機率高達 `35.0%`，而且還裸露在公網大門上），必須立刻拉起 `24 小時` 緊急止血；反觀漏洞甲雖然理論基礎分 `8.6` 比較高，但還沒達 `9.0` 嚴重門檻，且被實際利用的機率只有 `0.3%` 又躲在內網離線腳本裡，當然不能讓它排擠漏洞乙的救火資源。
3. **開源 0-day 的通報管道選擇**：
   - **(B) 完全正確**。如果選 (A) 直接發公開 PR，你的 Commit Diff 跟測試案例等於當場向全世界廣播「這裡有個洞、照這樣打就會穿」，駭客的自動化爬蟲會在幾分鐘內拿去狂掃還沒升級的伺服器；選 (C) 則是未經協調就把 0-day 擴散到公開社群，同樣嚴重違反 CVD 協調揭露原則。
4. **Safe Harbor 安全港的失效邊界**：
   - **完全不受保護，你已經跨出 Safe Harbor 的紅線了**。當你用自己的測試帳號 A 讀到測試帳號 B 的訂單時，就已經完成「最小無害驗證」，足以百分之百證明 BOLA 漏洞存在。後面寫腳本去撈 500 位真實客戶的個資與交易紀錄，屬於嚴重的**過度蒐證與未授權傾印資料**，不僅多數 Bug Bounty 平台會直接取消你的獎金並永久封號，在法律上更可能直接觸犯《刑法》第 359 條無故取得電磁紀錄罪。
