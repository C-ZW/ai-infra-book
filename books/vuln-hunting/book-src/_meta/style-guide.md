# 寫作契約（Style Guide）—《邊界失守》

## 1. 讀者校準（Calibration Only — 不入內文）

- **目標讀者**：具備 7 年以上實務經驗的資深後端工程師，熟練 TypeScript / Node.js（NestJS、Express）、MySQL / PostgreSQL、Redis、Docker、Kubernetes、AWS 基礎服務、單元測試與 CI/CD；具備 Rust、C FFI、原生執行時期底層與 AI Agent 工作流的實作探索背景。
- **已知（Assume-known，直接切入不贅述）**：HTTP/TCP/TLS 基礎、關聯式資料庫交易與索引、Redis 資料結構、容器與 K8s 基本物件（Pod/Deployment/Service/Ingress）、TypeScript/JavaScript 事件迴圈、基本 CI/CD 與 Git 工作流。
- **從零建立（Teach-from-zero）**：攻擊者視角的不變量破壞思維、協議解析差異、進階 Web/API/分散式狀態機漏洞挖掘、密碼學實作破口、Linux 核心與容器隔離邊界、x86_64/ARM64 二進位記憶體佈局、`ptmalloc2` 堆積機制、ROP 與現代緩解繞過、Rust/FFI 記憶體邊界、CodeQL 與灰箱 Fuzzing、漏洞揭露與資安職涯落地。
- **讀者語域（Register）**：`specialist`（同行工程師對話語氣）。直接切入系統架構、底層機制、邊界條件與實作細節，禁止基礎名詞鋪陳、禁止勵志或商業吹捧。
- **個人材料規則（硬性）**：上述背景**僅供深度校準**。書中**絕不出現**讀者的真實姓名、任職公司、真實客戶或個人履歷專案。所有實戰場景一律使用全書共享的虛構系統 **NexusPay** 或公開已揭露的 CVE／開源軟體案例。

## 2. 語言與文風契約（zh-TW）

- **語言**：繁體中文（台灣工程用語）。嚴禁簡體字與中國大陸術語（由 `_meta/lint.config.json` 以 ERROR 強制攔截）。
- **白話直述，動詞優先**：寫給人讀的中文，不是譯稿。一句話唸出聲要像懂行的資安研究員對資深後端同行說話。
- **禁止翻譯腔模式**（由 linter 以 WARN 偵測，修稿時人工重寫，禁止批次取代）：
  - 「進行／加以」＋動作名詞 → 直接用動詞（進行分析 → 分析）
  - 「透過…的方式」 → 用／靠／以
  - 「在…的情況下」 → 當／若／…時
  - 「對於…而言」 → 對…
  - 「存在著」 → 有
  - 「是…的」空殼斷言連用 → 拆掉空殼
  - 「作為（一個）…」開頭 → 換主語直述
- **敘事深度注入（Instructional + Narrative 融合）**：本書採 `instructional` 骨架以保證實作可驗證，但在「機制與推導」與「故障模式與防禦」兩節**必須達到深度技術專書水準**——追到規範條文、原始碼行級邏輯、記憶體位元組配置與真實 CVE 演進脈絡，禁止教科書式的清單列舉。
- **節奏**：一段一個論點；長句推導後接短句落點；名詞化三連以上拆句；代名詞指涉必須唯一明確。

## 3. 書型契約（Form: `instructional`）

### 固定章節骨架（Verbatim from `lang/zh-TW.json`）

每章必須依序包含以下六個 H2 標題（不可增減、不可改名、不可調換順序）：

1. `## 從你已知的出發`
2. `## 機制與推導`（**首個 H3 必須為 `### 攻擊者目標與實質影響`**，開宗明義交代攻擊者利用本章技術最終要拿到的實質收益、業務／系統破壞面，以及它如何作為跨層攻擊鏈的跳板，再切入底層機制推導）
3. `## 故障模式與防禦`
4. `## 動手做`
5. `## 自我檢核`
6. `## 延伸閱讀`

### 深度與實例標準

- **Worked Example（真實數字端到端推導）**：每章至少 1 個 fenced code block 內的完整推導，使用真實數值，不可只點名公式或工具。本領域的「真實數字」包含：
  - 線路層 HTTP/1.1、HTTP/2、TCP/TLS 位元組長度與封包內容（如 `Content-Length: 43` 與 chunk hex 長度對齊）
  - 資料庫查詢計劃、交易隔離時序毫秒差與併發競爭視窗
  - 64 位元虛擬記憶體位址、chunk 大小與對齊（16-byte alignment）、ASLR 熵位元數、Safe-Linking `pos >> 12` XOR 實算
  - 密碼學區塊大小（16 bytes）、Nonce 長度（96 bits）、生日碰撞機率量級
  - CVSS v4.0 向量評分、EPSS 機率與 Fuzzing 覆蓋率／exec/sec 指標
- **決策框架優先於工具清單**：不得只列出工具名稱而不拆解其底層機制（例如提到 AFL++ 必須講清邊緣覆蓋率位圖與 forkserver；提到 CodeQL 必須講清 AST/CFG/DataFlow 關聯式資料庫查詢）。
- **練習題與動手做契約**：
  - 每個「動手做」與「自我檢核」均須標註**難度**（`入門` / `進階` / `挑戰`）與**預估時間**（如 `45 分鐘`）。
  - 每個練習區段後方必須緊接 `### 參考解答`（或 `### 解答與解析`）子節，提供可執行的驗證步驟與關鍵推理。

### Lab 預算與環境慣例

- **Ch01–Ch26（本地零成本環境＋逐章外部靶場對照）**：全部主實驗基於本地 Docker Compose、Node.js 22、PostgreSQL 16、Redis 7、Nginx、Linux/C（gcc/clang）、Rust（cargo）、Ghidra、gdb/pwndbg，零雲端費用、離線可重現；同時每章於「動手做」附上精確對應的 **PortSwigger Web Security Academy（Practitioner/Expert）**或 **pwn.college** 模組檢查點與卡點提示（教思維，不提供照抄解答）。
- **Ch27–Ch37（核心 QEMU/VM、真實開源專案與實戰靶場路線）**：延續本地容器／`kind`/k3s／QEMU Linux Kernel VM 環境，並直接操作真實開源專案（CodeQL 變體掃描、AFL++/`cargo-fuzz` 撰寫外部 Harness、OSS-Fuzz 流程）與公開 VDP/Bug Bounty 範圍；凡需雲端帳號或付費環境之選做延伸均明確標註成本與本地替代方案。
- **授權與倫理邊界**：書中所有攻擊演練僅針對本地建置的 NexusPay 靶機、授權靶場（PortSwigger、pwn.college）或具明確漏洞揭露政策（VDP/Bug Bounty）之目標。

## 4. 橋接契約（Bridging Contract）

- 禁止第二人稱閒聊式比喻與生活類比；僅允許**技術機制對技術機制**的結構同構橋接。
- 每章最多 1 個橋接，於首次引入概念時明確標出「來源機制 → 目標機制」、「成立邊界」與「失效邊界」。
- 任何單一來源概念全書最多使用 3 次（受 `outline.md` Bridge Registry 鎖定）。
- **淡出排程（Fade-out Schedule，37 章三等分）**：
  - **前三分之一（Ch01–Ch12）**：節制使用外部後端機制橋接（每章 ≤1，可為 `none`）。
  - **中三分之一（Ch13–Ch24）**：優先交叉引用書內前章已建立的資安原語，外部橋接僅在跨領域切換時使用。
  - **後三分之一（Ch25–Ch37）**：一律 `none`，純使用本書與資安領域原生詞彙。
